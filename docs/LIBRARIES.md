# Библиотеки общего приложения

## Стек v0.3.0

Версии ядра сохранены при объединении с серверной платформой. Один сервер использует SVG-адаптеры и общее Java-ядро; отдельный внешний сервис моделирования не нужен.

| Компонент | Версия | Работа в приложении |
|---|---|---|
| Apache Batik parser / transcoder / codec | 1.20 | Семантическая геометрия SVG и серверная растеризация обычных планов |
| JGraphT | 1.5.3 | Граф и Дейкстра для двух стратегий маршрутизации |
| Jackson | 2.22.4 | JSON API, параметры и сохранённые снимки; версии согласованы BOM |
| Javalin / Jetty | 7.2.4 / 12.1.14 | Сервер API и собранного интерфейса |
| SQLite JDBC | 3.54.1.0 | Локальная база пользователей, зданий, сценариев и запусков |
| HikariCP | 5.1.0 | Пул подключений к базе |
| Flyway | 10.15.0 | Миграции схемы SQLite |
| jBCrypt | 0.4 | Хеширование паролей |
| SLF4J / Logback | 2.0.13 / 1.5.6 | Серверное журналирование |
| Logback / SLF4J | 1.5.38 / 2.0.20 | Журналирование сервера |
| TypeScript / Vite | По `web/package-lock.json` | Проверка типов и сборка браузерного интерфейса |
| JUnit Jupiter / AssertJ | 5.10.2 / 3.26.0 | Проверки Java-ядра и сервера |

Java 25 и Maven 3.9.9+ используются для обоих модулей; интерфейс собирается Node.js 22/npm. Полная команда из корня — `mvn -B clean verify`; она также выполняет `npm ci` и сборку `web/dist`. Дополнительно `npm --prefix web test` проверяет воспроизведение. Итоговая проверка выпуска документируется в [RELEASE_v0.3.0.md](RELEASE_v0.3.0.md).

Источники серверной платформы и сохранённое авторство: [INTEGRATION.md](INTEGRATION.md). Исторический перечень уведомлений ядра ниже и в [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) не является полным новым деревом серверных транзитивных зависимостей.

## Историческая интеграция ядра v0.2.0

Версии зафиксированы для v0.2.0. Подключаются готовые Maven-артефакты открытых проектов; копии исходных репозиториев в приложение не добавляются. Все вычисления работают локально, внешние API и ключи не требуются.

## Подключённый стек

| Компонент | Версия | Для чего используется | Почему подходит |
|---|---|---|---|
| [Apache Batik](https://github.com/apache/xmlgraphics-batik/tree/batik-1_20), `org.apache.xmlgraphics:batik-parser` | 1.20 | Разбор SVG `path`, включая кривые и дуги, а также `transform` | Batik уже был назван в README. Готовый SVG-парсер заменяет неполный регулярный разбор, не требует нового интерфейса |
| [JGraphT](https://github.com/jgrapht/jgrapht/tree/jgrapht-1.5.3), `org.jgrapht:jgrapht-core` | 1.5.3 | Граф и алгоритм Дейкстры для маршрутизации с весами и параллельными проходами | Позволяет развивать маршруты, блокировки и алгоритмы потоков на одном графовом стеке |
| [Jackson Databind](https://github.com/FasterXML/jackson-databind/tree/jackson-databind-2.22.4), `com.fasterxml.jackson.core:jackson-databind` | 2.22.4 | JSON-запрос сценария и JSON-ответ расчёта | Соединяет существующие Java-модели и браузер, исключает ручную сборку JSON |
| [JUnit Jupiter](https://github.com/junit-team/junit-framework/tree/r5.10.2), `org.junit.jupiter:junit-jupiter` | 5.10.2 | Автоматическая проверка парсера, очередей, маршрутов и HTTP API | Использовался до обновления; сохранён совместимый тестовый стек |
| JDK HTTP Server, `jdk.httpserver` | Java 25 | Локальные статические файлы и API | Для одного локального приложения достаточно JDK; отдельный web-фреймворк пока не нужен |

Batik, JGraphT и Jackson выполняют разные части одного расчёта: SVG → предметная модель → граф и очереди → JSON → маршруты в браузере. Событийная модель эвакуации остаётся кодом проекта: наличие библиотеки поиска пути само по себе не моделирует движение толпы.

Java 25 сохранена из исходного `pom.xml`. JGraphT 1.5.x требует JDK 11+, Jackson 2.13+ — JDK 8+; выбранные зависимости совместимы с используемым JDK. Батик использует классы геометрии AWT и работает в headless-режиме без рабочего стола. Jackson-компоненты следует обновлять согласованно через BOM, а не отдельными случайными версиями.

## Что проверять вместе

Команда общего прогона из корня репозитория:

```bash
mvn -B -f evac_sim/pom.xml clean verify
```

Проверки относятся к поведению целого сценария:

- все прежние рабочие SVG-примеры по-прежнему читаются;
- кривые и преобразования дают ожидаемую геометрию; ошибочные ссылки, повторные id и нечисловые физические параметры отклоняются;
- очередь у одного прохода соблюдает интервал `1 / throughput`, в том числе при дробной пропускной способности;
- альтернативные выходы используются, блокировка меняет маршрут, отсутствие пути не превращается в успешную эвакуацию;
- число людей сохраняется, заполненность не подменяется вместимостью, расчёт воспроизводим;
- браузер вызывает Java API, а исполняемый JAR содержит нужные классы и ресурсы.

Наличие теста не означает калибровку физики. Проверку на реальных планах, контрольных данных и больших сценариях нужно провести отдельными этапами из [ROADMAP.md](ROADMAP.md).

## Что отложено

| Открытый проект | Решение сейчас | Когда вернуться |
|---|---|---|
| [OpenJFX / JavaFX](https://github.com/openjdk/jfx/tree/jfx21) | Упомянут в старом README, не подключён | Если будет принято требование нативного desktop-интерфейса. Сейчас браузер уже является оболочкой Java-сервиса |
| [JuPedSim](https://github.com/PedestrianDynamics/jupedsim) | Изучен как кандидат; не установлен и не выдаётся за протестированную зависимость | При сравнении микроскопической модели толпы: предоставляет пешеходную динамику, но потребует отдельного адаптера C++/Python, формата геометрии и проверки результатов |
| [Vadere](https://github.com/pedestrian-dynamics-HM/vadere) | Изучен как кандидат внешнего эталонного расчёта; не установлен | При сравнении моделей толпы и калибровке. Есть Java-приложение, CLI и модели Optimal Steps / Social Force; это полноценный движок со своим форматом сценариев |
| [Eclipse SUMO](https://github.com/eclipse-sumo/sumo) | Не выбран для начального здания | Если задача расширится до эвакуации территории с дорожными сетями и разными видами транспорта |

Подключение сразу нескольких движков толпы потребовало бы синхронизации разных моделей состояния и времени. На начальном этапе выбран один расчётный путь и оставлена возможность сравнить его с отдельным движком позже.
